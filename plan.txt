--- LIKES/DISLIKES ---

Table: engagement_likes_aggregate
  - id              (int, primary key, auto increment)
  - elementId       (int, Craft element ID)
  - fieldId         (int, Craft field ID)
  - siteId          (int, Craft site ID)
  - likeCount       (BIGINT UNSIGNED, total number of likes)
  - dislikeCount    (BIGINT UNSIGNED, total number of dislikes)
  - dateCreated     (datetime)
  - dateUpdated     (datetime)

  Unique constraint: (elementId, fieldId, siteId)

Table: engagement_likes_votes
  - id              (int, primary key, auto increment)
  - aggregateId     (int, foreign key -> engagement_likes_aggregate.id)
  - userId          (int, nullable, Craft user ID)
  - sessionId       (string, nullable, for guest interactions)
  - value           (TINYINT, 1 = like, -1 = dislike)
                    Mutually exclusive per user/session per aggregate row.
                    Casting a like removes any existing dislike and vice
                    versa. Casting the same value again removes the vote
                    entirely (toggle off).
  - dateCreated     (datetime)
  - dateUpdated     (datetime)

  Unique constraints:
    - (aggregateId, userId)
    - (aggregateId, sessionId)
  Identity rule:
    - Exactly one of userId or sessionId must be set per row.

--- FAVORITES ---

Table: engagement_favorites_aggregate
  - id              (int, primary key, auto increment)
  - elementId       (int, Craft element ID)
  - fieldId         (int, Craft field ID)
  - siteId          (int, Craft site ID)
  - favoriteCount   (BIGINT UNSIGNED, total number of users who favorited)
  - dateCreated     (datetime)
  - dateUpdated     (datetime)

  Unique constraint: (elementId, fieldId, siteId)

  Note: favoriteCount is always maintained regardless of the field's display
  mode. When the field is configured for personal-only mode, the count is
  stored but not exposed in the frontend widget. The field setting controls
  visibility, not storage.

Table: engagement_favorites_entries
  - id              (int, primary key, auto increment)
  - aggregateId     (int, foreign key -> engagement_favorites_aggregate.id)
  - userId          (int, nullable, Craft user ID)
  - sessionId       (string, nullable, for guest interactions)
  - dateCreated     (datetime)
  - dateUpdated     (datetime)

  Unique constraints:
    - (aggregateId, userId)
    - (aggregateId, sessionId)
  Identity rule:
    - Exactly one of userId or sessionId must be set per row.

6. Incremental aggregate write-path refactor (performance-critical)
- Schema alignment + naming consistency:
  - Rename ratings tables to match plugin namespace conventions:
    - `ratings_aggregate` -> `engagement_ratings_aggregate`
    - `ratings_votes` -> `engagement_ratings_votes`
  - Rename ratings vote foreign key column for consistency:
    - `topId` -> `aggregateId`
  - Update records/services/controllers to use renamed tables/column.
  - Keep `Install.php` as source-of-truth for this development-phase
    plugin (no legacy migration path required yet).
- Replace per-interaction recount behavior with incremental aggregate
  updates for all three feature types, so each interaction only touches:
  - one interaction row (vote/entry)
  - one aggregate row
- Favorites:
  - On add favorite entry: `favoriteCount = favoriteCount + 1`
  - On remove favorite entry: `favoriteCount = favoriteCount - 1`
- Likes/dislikes:
  - On new like: increment `likeCount`
  - On new dislike: increment `dislikeCount`
  - On toggle off active vote: decrement active side
  - On switching like <-> dislike: decrement old side and increment new side
- Ratings:
  - Replace recount-on-cast with delta updates.
  - Add a persisted running integer sum field (`ratingSum`) to avoid
    floating-point drift and guarantee exact aggregate math.
  - Remove physical `average` column from the ratings aggregate table.
  - Expose `average` as a derived runtime value:
    `average = ratingSum / voteCount` (or `0` when voteCount = 0).
  - Maintain:
    - `voteCount`
    - `ratingSum`
    - derived `average`
  - Apply deltas by interaction type:
    - new vote: `voteCount + 1`, `ratingSum + newRating`
    - vote change: `ratingSum + (newRating - oldRating)`
    - vote delete: `voteCount - 1`, `ratingSum - oldRating`
- Implement updates inside DB transactions to ensure interaction row and
  aggregate row stay consistent under concurrency.
- Keep force recount tooling as recovery/repair (manual/admin), not as
  the hot path for normal interactions.

8. Querying
- Goal: make querying feel Craft-native by using field-handle methods on
  element queries, not a separate "cross-entry" API concept.
- Keep the current read access pattern unchanged:
  - `entry.rating.average`, `entry.likes.likeCount`,
    `entry.favorites.favoriteCount`, etc.
- Primary query pattern for all three field types:
  - `craft.entries().<fieldHandle>(criteria)`
  - Example: `craft.entries().rating({ enabled: true, minAverage: 4 })`
- Query criteria should be available consistently across all three types:
  - common keys:
    - `enabled`
    - `siteId`
  - `enabled` definition:
    - effective enabled state for this field on this entry
    - use per-entry override when allowed, otherwise field default
  - ratings keys:
    - `minAverage`, `maxAverage`
    - `minVoteCount`, `maxVoteCount`
    - `hasVotes` (`true`/`false`)
  - likes keys:
    - `minLikes`, `maxLikes`
    - `minDislikes`, `maxDislikes`
    - `minTotalVotes`, `maxTotalVotes`
    - `minScore`, `maxScore` (`score = likeCount - dislikeCount`)
  - favorites keys:
    - `minFavorites`, `maxFavorites`
    - `hasFavorites` (`true`/`false`)
- No-aggregate defaults:
  - when no aggregate row exists, all counts default to `0`
  - ratings average defaults to `0`
- Sorting support (native `orderBy(...)`, handle-aware):
  - sort keys include the field handle to avoid ambiguity when multiple
    engagement fields exist on one entry type
  - sort key format:
    - ratings: `<handle>__average`, `<handle>__voteCount`
    - likes: `<handle>__likes`, `<handle>__dislikes`,
      `<handle>__score`, `<handle>__totalVotes`
    - favorites: `<handle>__count`
  - Example:
    - `craft.entries().rating({ minAverage: 3.5 }).orderBy('rating__average desc')`
    - `craft.entries().likes({ minTotalVotes: 10 }).orderBy('likes__score desc')`
- Query criteria validation behavior:
  - unknown keys are ignored
  - invalid values are ignored for that key
  - `min > max` yields an empty result set
